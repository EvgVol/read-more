# Read More: дизайн удобочитаемых учебных материалов

## Цель

Превратить длинную теорию курса ML-инженера в последовательные учебные страницы, которые начинающий студент может читать небольшими шагами, понимать связи между понятиями, выполнять практику и возвращаться к последнему месту обучения.

Первый пилотный результат — переработанный урок «Python для анализа данных». После проверки пилота тот же формат применяется к остальным трём урокам модуля Python, затем масштабируется на остальные 24 урока курса.

## Контекст текущей реализации

- Материал хранится в модели `LessonMaterial` в пяти полях: `objectives`, `theory`, `practice`, `self_check`, `resources`.
- Теория генерируется командой `ml_theory.py` как длинный Markdown-текст с заголовками второго уровня и повторяющимися абзацами.
- Markdown обрабатывается фильтром `render_markdown`, который поддерживает fenced code и tables, экранирует HTML и ограничивает небезопасные ссылки.
- Страница тренера отображает только один текущий этап урока, сохраняет прогресс по пяти этапам и уже имеет историю обучения.
- Основной недостаток находится в структуре и подаче контента, а не в модели прогресса: студент видит большие текстовые блоки без достаточных промежуточных ориентиров.

## Дизайн-решение

Сохраняем Markdown как основной формат авторинга, но вводим обязательный учебный шаблон для каждого смыслового раздела. Это позволяет улучшить содержание без миграции базы данных и сохранить совместимость с существующими материалами.

Каждый крупный раздел должен по возможности включать:

1. короткое объяснение идеи;
2. ответ на вопрос «зачем это нужно ML-инженеру»;
3. ключевые термины;
4. пошаговый разбор;
5. небольшой пример;
6. код или псевдокод, если он помогает понять тему;
7. типичные ошибки;
8. практическое задание;
9. вопросы для самопроверки;
10. краткий итог и переход к следующему разделу.

Шаблон не означает, что каждый раздел должен быть одинаковым по объёму. Для математической темы важнее формула и визуальная интерпретация, для инженерной — алгоритм, код, диагностика и production-контракт.

## Визуальная система

Используем учебные схемы и диаграммы, а не декоративные изображения. Каждое изображение должно объяснять связь, процесс или структуру и иметь подпись и альтернативный текст.

В первом пилоте используются:

- схема «файл → проверка → преобразование → результат»;
- схема границы между сырыми данными, preprocessing и результатом;
- схема цикла проверки: гипотеза → код → тест → метрика → вывод.

Предпочтительный формат — SVG или встроенная безопасная HTML/SVG-схема, если она доступна в текущем frontend-стеке. Если схема хранится как файл, она размещается среди статических ресурсов курса и подключается через Markdown с понятным `alt`-текстом.

## Визуальные маркеры текста

Markdown-авторинг должен поддерживать понятные маркеры:

- `Важно` — правило или ограничение, которое нельзя пропустить;
- `Запомните` — краткая формулировка ключевой идеи;
- `Типичная ошибка` — часто встречающийся неправильный ход;
- `Практика` — действие студента;
- `Проверка себя` — вопрос или короткая проверка понимания.

Маркеры должны отличаться не только цветом: у каждого есть текстовая подпись, семантический класс и доступное представление для клавиатуры и скринридера.

## Структура страницы чтения

На первом этапе сохраняется существующее деление урока на пять этапов и история обучения. Внутри этапа «Теория» добавляются:

- компактное оглавление разделов;
- видимая иерархия `h2`/`h3`;
- короткие абзацы и списки вместо длинных полотен;
- визуальные callout-блоки;
- таблицы для сравнений;
- кодовые блоки с пояснением до или после примера;
- подписи к схемам;
- переход в конце каждого крупного раздела.

Оглавление не должно превращать страницу в отдельную сложную навигационную систему. Для пилота достаточно якорных ссылок на заголовки текущего материала и понятного возврата к началу теории. Сохранение последнего раздела чтения добавляется после проверки базовой структуры и не должно ломать существующий прогресс по пяти этапам.

## Итерации

### Итерация 0: контракт и эталон

- зафиксировать Markdown-синтаксис для callout-блоков;
- добавить тесты рендеринга заголовков, списков, таблиц, кода, ссылок и callout-блоков;
- определить ограничения по изображениям, alt-тексту и внешним ссылкам;
- сохранить текущие материалы как совместимый legacy-вариант.

### Итерация 1: первый урок

- переработать «Python для анализа данных»;
- построить короткие смысловые секции;
- добавить три учебные схемы;
- добавить примеры и практический чек-лист;
- отобразить оглавление и маркеры в тренере;
- проверить desktop/mobile и прохождение пяти этапов.

### Итерация 2: модуль Python

- переработать уроки NumPy, Pandas, Git/окружения/Jupyter;
- сохранить единый визуальный язык;
- подобрать схемы под специфику каждого урока;
- сравнить читаемость и объём HTML с первым пилотом.

### Итерация 3: навигация чтения

- добавить переходы между подразделами;
- добавить индикатор положения внутри теории;
- сохранять последний открытый раздел;
- не изменять семантику завершения этапа и историю событий.

### Итерация 4: остальные модули

- применять проверенный шаблон к математике, EDA, классическому ML, Deep Learning, NLP, MLOps и итоговому проекту;
- для каждого урока поддерживать минимум один самостоятельный пример и один визуальный объект, если тема допускает визуализацию;
- сложные темы разбивать на несколько коротких подразделов, а не увеличивать размер одного текста.

### Итерация 5: контроль качества

- проверить структуру всех 28 уроков;
- проверить отсутствие длинных сплошных блоков без заголовка или списка;
- проверить наличие alt-текста и подписей;
- проверить мобильную версию;
- проверить корректность Markdown-безопасности;
- проверить сохранение прогресса и истории обучения;
- проверить производительность страниц после добавления схем и оглавления.

## Технические границы

- Не менять модель `LessonMaterial` на этапе пилота.
- Не добавлять тяжёлый визуальный редактор.
- Не подключать внешние CDN для изображений и библиотек без отдельного решения.
- Не превращать теорию в набор декоративных карточек: визуальное оформление должно поддерживать последовательное чтение.
- Не смешивать прогресс чтения по подразделам с завершением учебного этапа до отдельной проверки UX.
- Все новые HTML-маркеры должны проходить экранирование и не ослаблять фильтрацию небезопасного Markdown.

## Критерии успеха пилота

Пилот считается готовым, если:

- первый урок имеет ясную иерархию заголовков;
- в нём есть короткие абзацы, списки, минимум один кодовый пример, таблица или структурированное сравнение;
- есть минимум три осмысленные учебные схемы с подписями и alt-текстом;
- callout-блоки различимы текстом и визуально;
- студент может быстро найти нужный раздел через оглавление;
- переход к следующему разделу понятен без чтения всей страницы;
- существующие пять этапов, история и сохранение прогресса работают без изменений;
- тесты проверяют рендеринг и безопасность нового формата;
- страница не получает существенного регресса по времени ответа и размеру ресурсов.

## Не входит в первый пилот

- полная переработка всех 28 уроков;
- генерация персональных иллюстраций для каждого абзаца;
- автоматическое определение качества текста языковой моделью без ручной проверки;
- сложная аналитика времени чтения;
- изменение структуры базы данных;
- redesign всего сайта за пределами страницы курса.

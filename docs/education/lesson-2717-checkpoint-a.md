## 2. Целевая структура теории

### Раздел 1. Зачем Python используется в анализе данных

**Цель.** Понять, какие задачи решает Python в аналитическом pipeline и где заканчивается ответственность языка.

**Объяснение.** Python связывает чтение данных, проверку контракта, преобразования, расчёт метрик и сохранение результата. Библиотеки ускоряют работу, но не заменяют инженерное мышление: нужно понимать форму входа, типы, правила пропусков и ожидаемый результат.

**Пример.** Путь `CSV → Python-функция → проверка → агрегаты → JSON/таблица` на файле заказов.

**Частые ошибки.** Считать Python ML-моделью; читать CSV без проверки заголовков; смешивать загрузку, очистку и вывод в одной функции.

**Вопрос.** Почему корректный результат нельзя гарантировать только тем, что файл успешно открылся?

### Раздел 2. Структура Python-проекта

**Цель.** Научиться раскладывать код по ответственности и запускать его одинаково локально и в тестах.

**Объяснение.** Используем минимальную структуру:

```text
project/
├── data/orders.csv
├── src/data_summary.py
├── tests/test_data_summary.py
└── pyproject.toml
```

`src` содержит логику, `tests` — проверяемое поведение, `data` — входной пример. Путь к файлу приходит аргументом, а не зашит глобальной константой.

**Пример.** `python -m src.data_summary data/orders.csv`.

**Частые ошибки.** Импортировать код через запуск файла из случайной директории; хранить секреты и изменяемые пути в модуле; тестировать только `print`.

**Вопрос.** Почему функция, принимающая `path`, воспроизводимее функции, которая сама выбирает файл?

### Раздел 3. Типы данных и коллекции

**Цель.** Выбирать структуру данных по операции, которую нужно выполнить.

**Объяснение.** `str` представляет текст, `int` и `float` — числа, `bool` — состояние, `None` — отсутствие значения. Список удобен для упорядоченной последовательности, словарь — для доступа по ключу, множество — для уникальности. Схема строки заказа: `order_id: str`, `amount: float`, `status: str`.

**Пример.** Преобразование строки CSV в словарь с нормализованными ключами и явными типами.

**Частые ошибки.** Сравнивать строку `'10'` с числом `10`; считать `None` нулём без бизнес-правила; использовать список пар вместо словаря для частого доступа по ключу.

**Вопрос.** Какая структура подходит для проверки уникальности идентификаторов и почему?

### Раздел 4. Функции и контракты

**Цель.** Писать маленькие функции с понятными входами, выходами и ошибками.

**Объяснение.** Контракт описывает типы, обязательные поля, допустимые значения и поведение при нарушении. Функция загрузки не должна молча исправлять неизвестную схему. Для ожидаемой ошибки используется конкретное исключение с понятным сообщением.

**Пример.** `read_orders(path: Path) -> list[dict[str, object]]` проверяет существование файла и обязательные колонки.

**Частые ошибки.** Возвращать то список, то `None`; ловить `Exception`; скрывать ошибку пустым результатом; делать функцию одновременно загрузчиком, визуализатором и CLI.

**Вопрос.** Что должен узнать вызывающий код из сигнатуры и документации функции?

### Раздел 5. Чтение CSV-файлов

**Цель.** Загрузить табличный файл и проверить его минимальный входной контракт.

**Объяснение.** CSV — текстовый формат, поэтому разделитель, кодировка, заголовок и представление пустых ячеек должны быть явно определены. Чтение — только первый шаг; после него проверяем заголовки, количество строк и преобразуем поля.

**Пример.** `csv.DictReader` с `utf-8`, обязательными колонками `order_id,amount,status` и диагностикой отсутствующих полей.

**Частые ошибки.** Предположить запятую при фактической `;`; обработать заголовок как строку данных; не проверить дубликаты `order_id`; преобразовать пустую сумму через `float('')`.

**Вопрос.** Какие две проверки нужно выполнить сразу после создания `DictReader`?

### Раздел 6. Обработка пропущенных значений

**Цель.** Отличать отсутствие данных от нулевого значения и выбирать правило обработки осознанно.

**Объяснение.** Пустая сумма, строка `NA` и отсутствующий ключ — разные варианты. Правило зависит от поля: для обязательного идентификатора — ошибка, для необязательного комментария — `None`, для суммы — ошибка или явная политика замены, но не молчаливое обнуление.

**Пример.** `parse_amount` принимает пустое значение только при режиме `allow_missing=True`, иначе поднимает `ValueError` с номером строки.

**Частые ошибки.** Заменять все пропуски нулём; удалять строки без отчёта; считать пустую строку валидным текстом.

**Вопрос.** Почему пропуск в `order_id` нельзя обрабатывать так же, как пропуск в `comment`?

### Раздел 7. Исключения и обработка ошибок

**Цель.** Разделить ошибку входных данных, ошибку окружения и ошибку программирования.

**Объяснение.** `FileNotFoundError` сообщает об отсутствии файла, `csv.Error` — о проблеме формата, `ValueError` — о невозможном преобразовании. Перехватываем только ожидаемые исключения, добавляем контекст и не уничтожаем исходную причину без необходимости.

**Пример.** CLI печатает короткое сообщение пользователю, а функции оставляют типизированную ошибку для тестов.

**Частые ошибки.** `except Exception: return []`; пустой результат вместо ошибки; сообщение без имени файла и номера строки; обработка ошибки в нескольких слоях.

**Вопрос.** В чём разница между `raise` и `return None` для вызывающего кода?

### Раздел 8. Тестирование функций

**Цель.** Проверять контракт на нормальном, граничном и ошибочном входе.

**Объяснение.** Тест должен проверять наблюдаемое поведение: результат, тип ошибки, сообщение и отсутствие побочных эффектов. Минимальный набор — валидный CSV, пустой CSV, отсутствующий файл, пропущенная обязательная колонка и некорректная сумма.

**Пример.** `pytest` создаёт временный файл через `tmp_path`, вызывает функцию и сравнивает структурированный результат.

**Частые ошибки.** Тестировать только happy path; использовать реальный путь разработчика; проверять внутренние переменные вместо контракта; делать тест зависимым от порядка файлов в директории.

**Вопрос.** Какой тест докажет, что функция не маскирует повреждённую сумму пустым результатом?

### Раздел 9. Простой pipeline обработки данных

**Цель.** Собрать отдельные функции в прозрачный и повторяемый pipeline.

**Объяснение.** Pipeline имеет этапы `read → validate → parse → summarize → serialize`. Каждый этап принимает понятный результат предыдущего, а итог содержит число строк, список колонок, долю пропусков и сумму валидных заказов.

**Пример.** `summarize_orders(path)` вызывает функции по цепочке; CLI сериализует итог в JSON.

**Частые ошибки.** Смешать `print` с расчётом; изменить входной файл; считать невалидные строки валидными; не сообщить, сколько строк отброшено.

**Вопрос.** На каком этапе должен появиться отчёт о пропуске обязательного поля и почему?

## 4. Единый воспроизводимый пример

### Входной файл `orders.csv`

```csv
order_id,amount,status,comment
A-001,1200.50,paid,first order
A-002,800.00,pending,
A-003,invalid,paid,bad amount
A-004,450.00,cancelled,returned
```

### Контракт

- кодировка UTF-8;
- разделитель `,`;
- обязательные колонки: `order_id`, `amount`, `status`;
- `order_id` непустой и уникальный;
- `amount` — положительное число, невалидная сумма является ошибкой строки;
- `status` принадлежит множеству `paid`, `pending`, `cancelled`;
- `comment` необязателен.

### Функции и ожидаемый результат

`read_orders(path)`, `validate_headers(headers)`, `parse_order(row, line_number)`, `summarize_orders(rows)` и `main()` должны быть разделены. Для демонстрационного файла функция либо возвращает структурированный отчёт с одной диагностикой строки 4, либо завершает обработку с `ValueError`; вариант поведения фиксируется до публикации и одинаково отражается в тестах, rubric и CLI.

Рекомендуемый учебный режим: строгий — первая невалидная обязательная строка вызывает `ValueError("line 4: amount must be a positive number")`. Отдельный режим `--skip-invalid` можно добавить только после базового задания.

### Минимальный набор pytest-проверок

```python
def test_summary_for_valid_csv(tmp_path):
    path = tmp_path / "orders.csv"
    path.write_text(
        "order_id,amount,status\\nA-1,10.5,paid\\nA-2,2,pending\\n",
        encoding="utf-8",
    )
    result = summarize_orders(path)
    assert result["row_count"] == 2
    assert result["amount_total"] == 12.5


def test_missing_file_is_explicit(tmp_path):
    with pytest.raises(FileNotFoundError):
        summarize_orders(tmp_path / "missing.csv")


def test_invalid_amount_has_line_context(tmp_path):
    path = tmp_path / "orders.csv"
    path.write_text("order_id,amount,status\\nA-1,nope,paid\\n", encoding="utf-8")
    with pytest.raises(ValueError, match="line 2"):
        summarize_orders(path)
```

До интеграции пример будет прогнан в отдельном чистом окружении; публикация допускается только при прохождении всех примеров и тестов.

## 5. Практика с постепенным усложнением

### Уровень 1 — прочитать CSV и посчитать статистику

- **Условие:** написать `summarize_orders(path)` для валидного файла.
- **Вход:** CSV из двух валидных строк.
- **Ожидается:** `row_count`, `columns`, `amount_total`.
- **Критерии:** корректное чтение, числовой тип суммы, отсутствие глобального пути, тест happy path.
- **Подсказки:** начните с `csv.DictReader`; сначала распечатайте одну строку и её типы.
- **Эталон:** скрытый reference solution в тестовом пакете, не в пользовательском HTML.
- **Проверки:** валидный файл; пустой файл как отрицательный сценарий.

### Уровень 2 — пропуски, невалидные значения и ошибки

- **Условие:** добавить проверку обязательных колонок, пропусков и диагностик строк.
- **Вход:** файл с пустым `order_id`, пустой `amount`, `invalid` и отсутствующим файлом.
- **Ожидается:** конкретные `ValueError`/`FileNotFoundError` с контекстом.
- **Критерии:** нет `except Exception`, пропуски не превращаются молча в ноль, тесты на каждый класс ошибки.
- **Подсказки:** нормализуйте значение до преобразования; номер строки берите из цикла `DictReader`.
- **Эталон:** закрытый тестовый reference solution.
- **Проверки:** валидная строка; каждая невалидная причина отдельно.

### Уровень 3 — `data_summary.py` как мини-проект

- **Условие:** реализовать CLI, валидацию, структурированный JSON-вывод и полный набор тестов.
- **Вход:** путь аргументом командной строки и CSV.
- **Ожидается:** стабильный JSON с `row_count`, `columns`, `missing_ratio`, `amount_total`, `errors`.
- **Критерии:** разделение функций, повторяемость, читаемые сообщения, тесты позитивных/негативных веток, документация запуска.
- **Подсказки:** сначала стабилизируйте чистые функции, затем добавьте `argparse`; CLI не должен содержать бизнес-логику.
- **Эталон:** reference solution и набор проверок запускаются на сервере без исполнения произвольного кода пользователя.
- **Проверки:** обычный файл, пустой файл, неверный заголовок, пропуски, неверный тип, отсутствующий путь.

Система не выполняет произвольный Python пользователя внутри Django. На Checkpoint B интегрируются только декларативные проверки ответа, тестовые фикстуры и безопасные серверные проверки.
